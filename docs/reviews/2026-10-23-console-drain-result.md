# Console drain result — 2026-10-23

Implemented in the shared `feat/frontend-rewrite` checkout, without commits.

Owned changes: `vesta-launcher/src-tauri/src/servers/worker.rs`, new `worker_console.rs` (including seven unit tests), and this report. No `mod.rs` change was needed. Other shared-checkout modifications belong to the parent/other implementers.

- Console has an independent event-driven drain and one owned recovery/controller task, plus its existing socket. Client construction, player/status/operation reads, failure synchronization and console history GETs cannot suspend the drain. There are no per-message tasks. The socket resolves its session-renewal deadline concurrently with receiving, avoiding a session mutex held across slow authentication I/O.
- The existing 1,024-message ingress bound remains. Each drain turn takes at most 64 messages and yields. Events contain at most 64 lines and 48 KiB including JSON escaping/overhead. IPC keeps the existing subscription queues, rate limits, overflow markers and error behavior. The 100 ms flush runs only with console demand; without console demand only a coarse one-second demand check remains.
- Content truncation uses one bounded UTF-8-safe escaping scan, preserves the cursor and sets `truncated=true`. The same normalized line enters retention and delivery, preventing escaped-line replay/resync loops. Metadata that cannot fit is refused with resync.
- Recovery preserves the earliest outstanding loss floor, follows page cursors, and de-duplicates live/history cursors within the existing 5,000-line/2 MiB retention bound. Recovery revisions prevent an older response from clearing newer loss. Expired cursors fall back to retained history with an explicit gap. History arrival order and duplicate live replays cannot replace the independent live cursor with an older ring tail. Normal eviction is not reported as new loss.
- Abort-on-drop ownership cascades worker → drain → controller → socket. Console demand removal disposes its controller/socket within the flush interval, even during a hung history read. A separate all-demand watchdog cancels hung observations after the existing two-second idle grace (one-second detection cadence), releasing the streaming permit. Trust replacement/removal retain the existing parent-worker abort boundary. Existing client credentials, same-account scope, authorization, retry policy and Retry-After remain in use; trust/access failures stop streaming.
- Slow roster results are checked against current generation, roster revision, readiness, fingerprint and demand before caching/publishing. Visible operation history GETs skip while the parent's `tracks_operations(id)` is true, then resume normally.

Limits/integration: non-console observations still serialize with one another; their latency is not solved here. Recovery has one in-flight GET and can delay reconnect work until that GET completes, while the drain continues. Neither server retention nor local cursor de-duplication is infinite; an evicted cursor may replay, and sustained overload still produces truthful resync/gap markers. Native IPC throttling/backlog still governs end-to-end delivery latency. No real agent/Minecraft or UI session was started.
